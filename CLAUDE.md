# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Two codebases in one repo

This repo holds **two implementations of the same IPTV player**, both living on `main`, each in its own self-contained project folder (own sources, build scripts, `.gitignore` and build output — nothing builds into the repo root):

- **`rust/` — Bongo Player (ACTIVE; formerly `tvplayer`).** A clean rebuild on **libmpv + egui/eframe (wgpu) + tokio**. This is where new work happens.
- **`c/` — `miroiptv` (FALLBACK).** The original plain-C player on **SDL2 + libav + libcurl**. Kept working as a fallback while the Rust rewrite is validated. Touch it only when explicitly working on the C app.

Shared design docs stay at the repo root in `docs/`.

When a request is ambiguous, assume it targets the **Rust Bongo Player** app.

**Performance is the top constraint.** The whole point of this player is "small, fast, featherlight" — instant zap (~300 ms), one portable exe + DLLs, no installer. The C app was abandoned partly because it grew slow. No change should regress startup time, zap latency, or memory footprint.

## Commands

### Rust Bongo Player (primary — run from `rust/`)

```powershell
.\vendor\fetch-mpv.ps1               # one-time: vendor libmpv-2.dll + headers
cargo test                           # unit + integration tests (see rust/tests/)
cargo test --test test_epg           # a single integration-test file
cargo test <substring>               # a single test by name substring
cargo build --release                # -> rust\target\release\BongoPlayer.exe
.\target\release\BongoPlayer.exe --selftest   # headless self-check, no portal needed
cargo clippy --all-targets           # lint
cargo fmt                            # format
```

Package a portable zip (also from `rust/`; output stays in `rust\dist\`):

```powershell
.\build-zip.ps1                      # -> rust\dist\BongoPlayer-vX.Y.Z.zip
.\verify.ps1                         # smoke-test the built zip
```

### C `miroiptv` (fallback — Windows + MSYS2/MinGW64, run from `c/`)

```bash
./mk                 # incremental build -> c/build/miroiptv.exe (wraps make in the MinGW64 env)
./mk test            # build + run the C unit tests
./mk clean && ./mk   # fresh rebuild
./build-dist.sh      # build + package the portable zip (-> c/miroiptv-<ver>.zip)
./build-dist.sh --release   # build + `gh release create` (version derived from git tag)
```

`./mk` / `mk.cmd` exist because the codec DLLs only resolve inside MSYS2's MinGW64 shell. The C exe loads `assets/` **relative to the working directory**, so it must run from `c/`; `mk.cmd` and `build-dist.cmd` cd to their own folder, so they work from any directory.

### Running

Both apps take a portal on the command line: `--xtream user:pass@host:port`, or a bare stream URL for ad-hoc playback. `tv.bat` (repo root) is a personal launcher for the C app (via `c\mk.cmd`) holding real credentials and is **git-ignored** — never commit it or hardcode credentials.

## Rust architecture (the big picture)

The module tree is declared in `rust/src/lib.rs`. The non-obvious structure:

- **`player/` — the libmpv boundary.** `mpv_sys.rs` is the raw `unsafe` FFI (constants, structs, extern fns); `mpv.rs` is the safe wrapper around it. `player::spawn()` starts a **dedicated `mpv-player` thread** that owns *all* mpv interaction — never call mpv from elsewhere. The rest of the app talks to it through channels:
  - `Cmd` (LoadUrl, LoadWithHeaders, Pause, Stop, SeekRelative, CycleAudio/Subtitle, SetWindowSize, Quit) flows in.
  - `Event` (FileLoaded, PlaybackStarted, EndOfFile, Error, PropertyChanged) flows out.
  - `render.rs` renders mpv frames into a shared `FrameBus` of `RgbaFrame`s, which the egui layer uploads as a texture; `FrameFence` keeps a stopped stream's late frames off screen. Video is drawn *by mpv's render API into RGBA*, not by a windowed mpv.
- **`app.rs` — the egui app + all UX.** Owns the event loop, zap logic, search overlay, favorites, quality switching, and wires the guide (`guide_ui.rs`) to playback: a pick plays live through the relay, or catch-up from its start behind a wait screen; the guide's EPG is fetched in the background and kept in a cache file. This is the largest file; most feature work lands here. It is a shared bottleneck — do features **sequentially**, not in parallel, to avoid collisions. Its tests start the app without a window (`TvApp::start`) and run real frames on a headless egui context (`update_ui`), so keyboard flows and background fetches are tested end to end (`app::tests::Harness`, with a portal that answers from memory).
- **`relay/` — local HLS relay for live streams.** Live channels of an Xtream portal never go to mpv directly: mpv plays `http://127.0.0.1:<port>/live/<id>.ts` and the relay fetches the portal's HLS segments strictly in media-sequence order into that one never-ending TS response. A refused playlist refresh (HTTP 509) is retried — same edge URL, then a fresh token via the portal — while mpv plays from the ~3-segment cushion, so it never sees an error. Also opens the portal once per zap (mpv opened it twice) and keeps credentials out of mpv's URLs/logs. `Relay::local_url()` already starts fetching (prefetch), so the portal round trips overlap mpv tearing down the previous stream; a newer load cancels an unclaimed prefetch, and a session ends the moment mpv hangs up. Starting a session waits out "busy" answers (503, up to `busy_wait`) but fails fast on real errors; a 407 means the stream is refused to the account (RTL 4 UHD, every time): the relay answers mpv 403 at once, remembers it (`Relay::refused()`), and the app plays the channel's next best variant (`catalog::fallback_variant`). Catch-up/HLS VOD go through `Relay::vod_url()`: the finished playlist is fetched once and served from memory to both of mpv's opens (each portal open is a playlist generation of 2.5–10+ s, so it gets the long `vod_timeout`: asking again starts the generation over); segments still come straight from the portal, so seeking is mpv's own. `load_url()` in `app.rs` does the routing. An M3U source skips the relay. Its streams go straight to mpv, and only a load from an M3U source (`Cmd::LoadWithHeaders`) has the headers in its URL split off and handed to mpv as options of that one file (`player::loadfile_args`); any other load (`Cmd::LoadUrl`) goes to mpv byte for byte, as in 0.6.1, because an Xtream password may hold a `|`. The User-Agent goes as `user-agent`, the Referer as an `http-header-fields` entry (commas escaped), never as `referrer` — libmpv put that back as an empty string after the file, and every later load sent an empty `Referer:`. `Mpv::command` returns an error, it does not panic, on a NUL byte in an argument (a list line can hold one).
- **`portal/` — the sources' APIs.** `xtream.rs` implements the `Portal` trait for an Xtream portal, `m3u.rs` (`M3uPortal`) for an M3U list. An M3U list has only channels. `crate::m3u` reads it: a stable id per channel, and the headers a stream needs, carried in its URL Kodi-style (`url|User-Agent=…&Referer=…`). The id is the first 8 bytes of the SHA-256 of the channel's key, read as a big-endian number and shifted right by one bit so it is never negative; the key is its `tvg-id` when no other channel of the list has that one, else its name (both trimmed), and a repeated key is numbered `#2`, `#3` in file order. Favorites and presets hold these ids, so the hash and the shift never change. Its saved list (`config\cache\m3u-<id>.m3u`, `Portal::saved_catalog`; a list in a file is read as it is) shows at once while the fresh one downloads; an unchanged download changes nothing. A list over 128 MB (a Content-Length that says so, or the body as it comes; a file by its length), or with a NUL byte in its first KB (a video, an archive), is no channel list, and no more of it is read. `types.rs` holds the wire types (`LiveChannel`, etc.). HTTP is async via `reqwest` on a tokio runtime.
- **`catalog.rs`** builds the channel catalog, ranks stream quality (`quality_rank`/`quality_label`) and dedups to one best-quality entry per channel. An M3U catalog (`CatalogStore::kind`) zaps in file order and merges nothing, has no quality ladder and no adult content, and leaves a `CatalogNotice` when its list did not update. The guide's merge (`guide_channels_of`) returns at once for a list with no catch-up channel, which an M3U list never has. Up/down zap through a `ZapRing` (`CatalogStore::zap_ring`): positions in the catalog's one shared channel list (`Arc<Vec<LiveChannel>>`), worked out once per catalog, lock and marks, so a press copies nothing (`zap_channels()` is a copy, for tests). The catalog also holds an M3U source's defect marks (`set_defect`): the ring and the channel list's groups leave them out (the list shows them in its Defect channels group only), the search and the favorites name them.
- **`sources.rs`** — every source in `BongoPlayer.ini`: `source=<id>;<kind>;<name>;<address>` lines and `active=<id>`. The 0.6.1 line `portal=` stays, as a copy of the first Xtream source, and one default portal alone (an Xtream source with id 1, in use, no name of its own) is that line only. A name's `;` becomes a comma when it is saved, and a name equal to its kind's default in any language is stored empty (`SourceKind::is_default_name`). Data is kept per source (`Storage::set_source`): source 1 keeps `favorites.json`, `presets.json` and `last_watched.json`, the others carry their id (`favorites-2.json`). Those files of source 1 are 0.6.1's portal's, so an M3U list never becomes source 1 (`Sources::keep`): a new list gets 1 + the highest id, 2 at least, and a new portal takes 1 when no portal is saved and 1 is free (an older ini with a list as source 1 is read as it is). Switching sources (`TvApp::activate_source`) works like a start on the other one; the ini is written first, and when that write fails nothing changes (the toast names the failure). The settings' Bronnen pane (`settings_ui.rs`) adds, changes, deletes and switches sources. In it a disabled button is no Tab stop (`settings_ui::action_button`), and `o`, Down, Enter lands on the Server field (a list's Address field) of the source in use; the e2e scenarios M-add, M-switch and M-getphp count these Tabs.
- **`epg.rs`** parses EPG listings (handles entries carrying either `start` or `start_timestamp`). `Epg::new` cleans the portal's listing (`clean_entries`): the same programme twice becomes one, overlaps are cut, so one programme runs at a time.
- **`guide/`** — the guide's data, drawing nothing: `time.rs` (local days, the now-line target, `Playable`), `store.rs` (`EpgStore`, freshness, fetch order, the filter), `fetch.rs` (`EpgFetcher`: 2 requests at a time with the guide open, 1 closed, none while a stream starts; rests 5/10/30 s after failures, leaves a channel alone for 10 min after three failures in a row), `cache.rs` (`config\cache\epg-<host>_<port>.json`, never adult channels, never credentials), `logos.rs` (logos of the visible columns, PNG only, kept as files once they decode (an adult column's only in memory), the HTTP client made on the first logo). **`guide_ui.rs`** draws the guide (`GuideView::show`) and the wait screen and returns `GuideAction`s, as `settings_ui.rs` does. `g` opens the guide (`TvApp::open_guide`) on the column of the channel that plays, as near the page's middle as the edges allow (`center_guide_on_what_plays`: the column found by stream id, else by the name the guide merges variants on, `guide_column_of`; `GuideView::center_on` hands it to the next draw, which knows the page); a channel without a column opens the guide where it was, with a toast that names it (`GuideNoChannel`); the wait screen's reopen (`reopen_guide`) is unchanged. A held `g` opens or closes the guide and the channel list once (key repeats are ignored: `fresh_press`, `spend_key_repeats`). On an M3U source `g` opens the channel list (`channel_list_ui.rs`) instead.
- **`search.rs`** cross-catalog search over live / VOD / series (`ItemKind`).
- **`playback_health.rs`** is the **freeze/stall watchdog**: it keys off mpv's `paused-for-cache` property (observed as a string "yes"/"no") to detect a frozen picture and drive recovery / quality switching. Armed for live channels, not for VOD/catch-up.
- **`favorites.rs` / `storage.rs` / `presets.rs`** handle persistence (favorites, last-watched-for-resume) under the platform config dir.
- **`shortcuts.rs`** holds `next_live_idx`, the wrap-around step that up/down zapping uses. The 0.5 NPO/RTL channel shortcuts are still in it (`find_live_by_name`, `npo_shortcut_id`, `news_npo`, `news_rtl`) but nothing calls them any more: digits are presets now and `n` opens the news list from the news rules. They stay until a cleanup removes them.
- **`zap.rs`** paces up/down zapping (`ZapPacer`): a lone press zaps at once; quick presses or a held key only flip the names and load where the user stops. The channel list's moves are presses of the same pacer. A start that comes due for the channel that plays loads nothing (`TvApp::plays`; a stream that has ended is no stream that plays).
- **`bad_streams.rs`** — defect marks of an M3U source. A channel whose start ends without a first picture (an mpv error, a refused load, an eof once the reload budget is spent or while the user flips on, the stall watchdog; `TvApp::note_start_failure`) is a suspect; another channel's first picture within 2 minutes confirms it (`note_first_picture`), else the suspicion lapses. A confirmed suspect is marked only when the check of its address (`stream_check.rs`) finds it dead too (`drain_stream_checks`), so a Wi-Fi drop of any length marks no good channel. Its own picture clears its suspicion and its mark; a marked channel that fails again is marked anew at once, with no check. A channel that has played since it was picked is never a suspect (`current_has_played`, the flag the M3U frame drop reads too). Marks last 7 days, per source in `bad_streams.json` / `bad_streams-<id>.json` (stream ids and unix times only), read when the source's catalog loads (`refresh_defects`) and expired with every new copy of the list and on F5 (`expire_defects`); the file goes when its source is deleted or saved with another address (`Storage::remove_source_files`, `remove_bad_streams`). app.rs hands every change to the catalog.
- **`stream_check.rs`** — the check before a defect mark: one GET of a confirmed suspect's address with the channel's own User-Agent and Referer (libmpv's `libmpv` when it names none), header values as bytes, and certificates verified: a certificate or TLS handshake it cannot verify leaves the channel unchecked, so unmarked. 5 s for the connection and the headers, the status only. 400 or more, no connection, or no headers within 5 s marks it (`Answer::is_dead`); 2xx/3xx drops the suspicion; anything else marks nothing (an address it cannot ask, a certificate it cannot verify, a redirect that never ends, an answer that is no HTTP it reads, a hang-up before a reply once connected; a server that hangs up during an https handshake counts as no connection, so it marks). It never asks the server of the stream that plays (`same_server`: scheme, host, port): on a paid list one account serves every channel and its portal allows one session, so such a suspect is not marked, and every M3U load drops the checks that wait or run on its server (`StreamChecker::forget_server`). At most one check per channel and 4 at once (`StreamChecker`), on the tokio runtime with a client built on the first check; the answers come through a slot `update_ui` drains. A switch of source, or a save that puts a source in use, drops the running checks (`install_portal`). The address never reaches the log (`Check` has no `Debug`). This is the only network the defect marks use.
- **`channel_list.rs` / `channel_list_ui.rs`** — `g` on an M3U source: the channel list over the running picture. `channel_list.rs` builds the groups (`ChannelGroups::build`: All channels, Favorites, the list's `group-title`s in natural A–Z order (the order of `natural_cmp`: Sport 2 before Sport 10, accents folded so that "Één" sorts among the E's), No group, Defect channels; Favorites, No group and Defect channels only when they hold channels) as positions in the catalog's channels (`CatalogStore::channel_groups`), and keeps the selection (`Cursor`); `channel_list_ui.rs` draws the rows on screen only and returns `ListAction`s. A move starts the channel behind the list through the app's one `ZapPacer`; Enter closes and plays, Esc/g close; opening drops a flip that waits on the main screen, so it starts nothing. The groups are built when the list opens and again while it is open when the catalog, the marks or the favorites change; the selection keeps its channel, else its row, but the channel that plays is followed into All channels when it leaves its group (a retry in Defect channels that works: its first picture clears its mark; `Cursor::follow`). A closed list keeps only the key of its last group (`channel_list_group`).
- **`window_drag.rs`** moves the borderless window (`t`) while the right mouse button is held. The window goes to where it was at the press plus how far the cursor has moved on the *screen* (Win32 `GetCursorPos`, physical pixels, one tiny FFI block), never by the pointer's place in the window: that shifts as the window moves and the window jitters after it. `app.rs::follow_right_drag` runs it every frame: a drag begins at a press and ends at the release, in full screen or maximized (the first move would restore the window and it would jump), without the focus, on F11 and when the border comes back. A release egui never hears of (another window took the mouse capture) would glue the window to the cursor, so while a drag runs it also polls `GetAsyncKeyState` (bit 15 only), which reads the *physical* buttons: with swapped buttons (`SM_SWAPBUTTON`, read once at the press) the physical left one. Idle it makes no Win32 call, command or repaint; a drag logs one debug line when it begins and one when it ends, with the reason. The mouse (cursor, swap, button state) comes from `TvApp::mouse` so the tests can put their own there.
- **`i18n.rs`** holds every user-visible text in NL/EN/DE (`t`, `tr` with `{0}` placeholders); **`settings.rs`** the preferences in `settings.json` (language, zap reversal, PIN hash, news rules); **`settings_ui.rs`** the settings overlay (`o`) and the first-start language screen, which return actions for `app.rs`; **`pin.rs`** the PIN hash and attempt limit; **`news.rs`** the news rules; **`redact.rs`** masks credentials in anything logged.

### Gotchas worth knowing

- **Names come from `lib.rs`.** `APP_NAME` ("Bongo Player") is what users see; `APP_ID` ("BongoPlayer") names the exe, `BongoPlayer.ini`, `%APPDATA%\BongoPlayer\config\`, the log file and the portal User-Agent. Crate names differ again (`bongo_player` lib, `BongoPlayer` bin), so the default log filter is built from `module_path!()` — never hardcode crate names there, or the app's logs go silent. `legacy.rs` migrates the pre-rename `tvplayer` data (`%APPDATA%\tvplayer\config`, `tvplayer.ini`) once on first start; keep it until no tvplayer installs remain.
- **Never route live Xtream HLS straight to mpv.** libav gives up on the first refused playlist refresh (`hls: Failed to reload playlist` → eof → frozen picture); this portal refuses ~1 in 4 directly-played live streams around the first reload. The relay rides that out invisibly. As a last line, an unexpected eof on a live stream auto-reloads (`ReloadBudget`, 3/min) before giving up with a toast. An M3U source's streams do go straight to mpv (its servers are not this portal and have no session rule); the eof auto-reload and the stall watchdog are their last line too.
- **The portal allows one session per account, newest wins, and throttles bursts.** Every load or stray request (a leftover relay session, a prefetch, mpv's ytdl_hook retrying a URL) takes the session from the stream being watched. A held arrow key used to open ~30 sessions a second (each with an EPG fetch): the portal answered 503 and stayed slow for minutes. Hence the zap pacer, relay sessions that stop with their player, and mpv's built-in Lua scripts (ytdl_hook among them) switched off in `player/mpv.rs`. The stall watchdog gives a stream that has not shown its first frame longer than the relay's `busy_wait` (`PlaybackHealth::stall_limit`), or its reloads restart the wait with a "herverbinden" toast.
- **`video-latency-hacks=yes` in `player/mpv.rs` is deliberate.** Measured zap → first frame 1.10 → 0.82 s. Keeping the audio device open across zaps (`gapless-audio=yes`) and software decoding were measured too and were slower — benchmark before changing mpv options; mpv's `playback-restart` event can fire before the picture, so time to its "playback restart complete" log line instead.
- **Benign mpv log noise is downgraded on purpose.** `player/mod.rs::effective_log_level()` demotes specific ffmpeg "error" lines to debug: HLS HTTP-EOF (Xtream portals close the playlist response without Content-Length) and the H.264 PPS/SPS/"no frame!" flood on every zap (B/P frames before the first keyframe). These are *not* real errors — don't "fix" them by removing the filter, or the log becomes unreadable on every channel switch.
- **Release profile is `panic = "abort"`** (plus thin LTO, `strip`, `codegen-units = 1`). No unwinding — a panic kills the process. Keep that in mind for anything relying on catching panics.
- **No UI text outside `i18n.rs`.** Add a key with all three translations; the table won't compile with one missing. Log lines stay English.
- **The catalog is the only adult filter.** Its lists leave adult content out while locked (`set_adult_unlocked`); never filter in UI code. Adult means the portal's `is_adult` flag and nothing else: there is no name rule (it hid the film *xXx*), so until the catalog has loaded nothing is known and the favorites list shows nothing. The unlock lives in memory only, so every start is locked, and `last_watched.json` records whether the stream was adult so it never resumes. A guide column merges a channel's variants and is adult when either is flagged; a pick from it marks the playing stream adult as well (`current_adult_hint`), for Lock and for `last_watched.json`. It is the only defect filter too: zapping, the channel list and the search read `CatalogStore::{zap_ring, channel_groups, is_defect}`, never a copy of the marks of their own.
- **The guide shows only channels with catch-up.** On this portal only the catch-up variants (`tv_archive=1`) carry EPG: 209 of ~13,000 channels. `catalog::guide_channels_of` merges each such channel's variants into one column (the live variant zapping picks, the catch-up twin for EPG and catch-up); zapping still uses every channel. The guide never asks for EPG until it was opened once, and the zap toast reads the guide's store before it asks the portal.
- **An M3U address is a credential.** It lives in `BongoPlayer.ini` only. Logs name an M3U source by its id and host (`source: m3u <id> (<host>)`, `redact::url_host`; `file` for a list in a file). Every log line, error text or toast that names an address or a stream URL goes through `redact()` or names only the id and host. `Source`, `SourceDraft`, `Sources`, `SettingsAction`, the settings' forms, the PIN dialog, `player::Cmd`, `args::Cli` (`--xtream`), `XtreamCreds`, `CredsSource`, `XtreamPortal` and `LastWatched` derive `Debug` in the crate's own tests only (`cfg_attr(test, derive(Debug))`): it would print an address, a stream URL, a password or a PIN, so a `{:?}` of one outside the tests does not build (the integration tests in `rust/tests/` compare such values as tuples). Besides the Xtream `/live/<user>/<pass>/` paths and `username=`/`password=` queries, `redact()` masks `user:pass@` in any URL, the query of a list's URL (`.m3u`, `.m3u8`, `get.php`, any letter case) and the Xtream short form `host/<user>/<pass>/<digits>[.ext]` that a paid list's stream URLs use. A token in the query of any other URL (`…/1.ts?token=…`) is **not** masked, so keep such a URL out of the logs. A channel without a name is named by its masked URL (`m3u::parse`). The saved list stays under `config\cache\`, never next to the exe. `rust/e2e/check-staged.sh` checks every source's secrets before a commit (`test-check-staged.sh` checks it).
- **A new M3U channel never shows the picture of the one before it.** One that mpv refuses, one the stall watchdog gives up, and one that ends before it has shown a picture (in an error, with the eof that ends its reloads, or with an eof while the user flips on) leaves the screen black (`stream_starting_since` and `current_has_played` with the `FrameFence`: `app.rs::stop_failed_start` for a refused load and for the watchdog's give-up, and the `Event::EndOfFile` arm, through `drop_the_picture_before_it`, for an error, for an eof the reloads did not get past and for an eof while the user flips on), not the old channel frozen under the new name. Which of them reads which flag: the `EndOfFile` arm reads `stream_starting_since` and `current_has_played` (through `drop_the_picture_before_it` and `note_start_failure`), and sets `ended` when an eof ends the stream while a flip waits; `stop_failed_start` reads `stream_starting_since` for a refused load, whether the channel played or not, and `ended` with `current_has_played` for a start that ended without a picture while the user flipped on; `check_stall` calls it only for a start that has not played (`current_has_played`), and `drop_flip` for that start when the flip is then dropped without a load (the list's Esc, g or another group, `g` opening the list, a target without an address; every drop goes through `drop_flip`), so "streamfout op …" comes at once. `ended` makes `TvApp::plays` say no, so a flip back to that channel loads it again; every load clears it, and the stall watchdog stays armed for a stream that has played. Once it has played, its own last frame stays under the error toast, also when its reloads fail, as on Xtream, which keeps 0.6.1's look.
- **An M3U start the stall watchdog would reload is given up instead.** A channel of an M3U list that has not played since it was picked (`current_has_played`, which `check_stall` asks) stops with "streamfout op …" when the watchdog fires (`stop_failed_start`, as for a load mpv refuses; that function itself asks `stream_starting_since`, and `ended` with `current_has_played` only for a start that ended while the user flipped on) and becomes a suspect; a reload would only start the 25 s wait over (`PlaybackHealth::stall_limit`). One that has played is reloaded as before, and Xtream is unchanged.
- **End-to-end tests run against `rust/e2e/mock_portal.py`** in a throw-away config folder (`BONGO_CONFIG_DIR`, `BONGO_INI`); see `rust/e2e/README.md`. They never touch the user's settings, PIN or credentials: with `BONGO_CONFIG_DIR` alone the ini is `BongoPlayer.ini` in that folder, never the one next to the exe. `run-scenario.ps1` refuses to start while Tab, Shift, Ctrl, Alt, Enter, Esc, Space, an arrow key, PgUp, PgDn, Home or End is held down, because winit turns a held key into a key press when the window gets the focus. A `TEXT:` step is followed by a 300 ms pause: egui handles the events of one frame together and a Tab moves the focus first, so a character typed in the same frame as the next Tab lands in the next field (real keys obey that rule too, but a person's gap before a Tab is far longer than a frame; in the e2e runs a frame took about 45 ms and the harness types a character every 46 ms). About one posted character in a hundred still gains a second one, because winit's loop calls `TranslateMessage` on the posted key down, which queues a `WM_CHAR` of its own next to the one the harness posts, and winit adds both to that key's text: a typing scenario that fails once, the setup prompt's login above all, gets one more run before anyone suspects the app (see `rust/e2e/README.md`).

## C architecture (fallback, brief)

Decoder runs on its own pthread pushing into bounded queues (16 video / 32 audio); the main thread consumes at VSYNC. A/V clock is **audio-master** — the SDL audio callback seeds `first_pts` and drives video pacing. Zap is async (`zap_prep_worker`) so the UI never blocks on HTTP/probe.
